## Findings that change the completion plan

1. **P1: manager intake is materially incomplete.** `components/people-view.tsx:280` offers teacher name, color, notes; students have name and level; rooms have name, capacity, comma-separated features. Notes are not an availability editor. `lib/planning-dataset.ts` snapshots teacher ID/name only. Availability, qualifications, required/preferred teacher, room/time restrictions and family relationships cannot be treated as already supported manager forms.
2. **P1: whole-snapshot confirmation exists, slice review does not.** `components/planning-dataset-confirmation-card.tsx:75` requires four unchecked attestations for people, class/session catalog, rosters and known completeness. Version/hash changes invalidate them. This is useful final certification, but provides neither explicit reviewed-no-restriction per entity/domain nor preservation of unrelated review work.
3. **P1: the main product teaches architecture.** `components/dashboard.tsx` foregrounds Planning Dataset, Constraint Model, compiler version, typed HARD/fixed nodes and compatibility validator; `components/app-shell.tsx` exposes enforcement version and partial validation. `/readiness` holds both final confirmation and the solver, while `/schedule` holds editing. Managers must discover the internal pipeline before building a schedule.
4. **P1: server safety exceeds UI guidance.** `components/schedule/schedule-view.tsx:486` computes displayed/edit draft duration from class default while server move logic derives canonical session duration. Distinct weekly durations can therefore show misleading edit previews even when protected on save. UI preview/button gating still uses legacy validation. Plan parity tests and session-aware presentation, not another mutation backend.
5. **P1 for second studio: week view hides rooms after three.** `components/schedule/schedule-view.tsx:471` uses `state.rooms.slice(0, 3)` and a three-column room grid. A fourth room can have valid assignments invisible in that view. Fixed layout/day conventions require genericization and >3-room acceptance coverage.
6. **P2: operational output is missing.** `components/settings-view.tsx:27` downloads Rulebook JSON named `DWDE-Rulebook-v…json`; this is not schedule print, staff CSV, or a published schedule. No schedule export action was found in schedule components.
7. **P2: mobile is real but incomplete.** `components/app-shell.tsx` switches below `md` to `mobile-schedule-view.tsx`; mobile has day/room timelines, touch dragging and detail display. Details instruct users to close and drag instead of offering equivalent accessible form editing. Desktop edit-mode disabling relies partly on pointer/CSS and button label matching (`schedule-edit-mode.tsx`), so keyboard behavior needs real tests.
8. **P2: existing repairs are valuable and should be reused.** `planning-repairs-view.tsx` routes structure issues to normal Classes editing/reviewed intake, and applies additive roster repair after review. A new Setup surface should own these queues and link into the same editors, not recreate a second planning intake authority.

## Proposed interaction model and review contract

Use **Setup**, **Schedule**, **History**, **Settings** as the primary destinations. Setup has Studio, Teachers, Classes, Dancers, Requirements, Preferences, Review. First visit offers the same sections in guided order; returning users see a nonlinear checklist. Existing People/Classes editors and repair commands remain reusable components/routes during migration. Advanced diagnostics retain Rulebook/compiler/version provenance without dominating ordinary screens.

Persist narrow review evidence keyed by studio + cycle + entity/domain with reviewer/time, reviewed fingerprint and answer disposition (restrictions entered or explicitly none). Derive MISSING/NEEDS_REVIEW/CHANGED_SINCE_REVIEW/BLOCKED rather than storing competing copies of canonical facts. Fingerprint only that domain's relevant canonical fields/structured rules and required relationships; room-capacity edits must not invalidate teacher availability review. Final certification still binds the full current immutable snapshot and the reviewed policy/context. A new version needs certification again, but unchanged slice evidence remains usable. Exact schema/authority decisions are owned by the canonical decisions and setup task, not this audit.

Block final certification/automatic generation on required unknowns, unresolved HARD semantics and deterministic invalid data. Allow saving incomplete drafts. Treat preferences and optional source provenance as warnings. Adoption additionally requires exact candidate base, complete assignment coverage, locks and fresh deterministic validation. Export/publishing must distinguish draft sharing from a current, approved operational schedule; never represent a stale or incomplete schedule as final.

Do not add a second rules system to power forms. Inventory facts remain Planning Dataset; scheduling requirements/preferences remain versioned structured policy; review metadata records human assessment only. Free text remains notes or an explicitly unresolved request until typed semantics are reviewed. Guided setup and repair queues must share the same commands and readiness reasons.
